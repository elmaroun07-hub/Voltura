# H-D51 — the PDF button names the calculation it was made from · 27 Sep 2026

**Fence.** In: the `/api/calculate` 200 response carries the id of the row it inserted;
the calculator page takes its PDF id from that response instead of guessing it from
history; the web's API base is applied in exactly one place, enforced by the type
checker. Out: everything inside the PDF renderer (D6's `??` defaults, D7's `25.0 years`),
D8, D52, `gate-check.sh`, adding a web test runner (D44), the History page, and
`Home.tsx:47` ("country-level" — B3 owns it; do not touch that line).
Branch: `heatshield/d51-calc-id`, off `main` at the tip at block open (`4aaeaec` when this
file was written — re-verify, and name what you find). G1 — no commits to `main`.

## The defect — read from the code on 27 Sep 2026 at `4aaeaec`

`Home.tsx:16–23` runs its own history query:

```ts
queryKey: [api.calculations.history.path],
queryFn: async () => {
  const res = await sessionFetch(api.calculations.history.path);   // no API_BASE
```

Production sets `VITE_API_URL`, so this request goes to the **static web origin**, whose SPA
fallback answers **200 with index.html**. `res.ok` is true, `res.json()` throws, the query
errors, and `calcId` (`Home.tsx:32`, `history[0].id`) is null. Observed live 11 Sep:
`GET https://voltura-web.onrender.com/api/history → 200`, twice, on page load (report D51).

Three failures sit in that one design, not one:

1. **D51 — the missing prefix.** Cold cache: the PDF button (`ResultsDisplay.tsx:256`,
   rendered only when `calcId` is truthy) never appears.
2. **D53 — two query functions, one key (P5).** `use-calculations.ts:6–15` (`useHistory`,
   prefixed, zod-parsed) and `Home.tsx` share `["/api/history"]`. With `staleTime: Infinity`
   (`queryClient.ts:114`), a visit to History first fills the cache; on the calculator page
   the mutation's `onSuccess` invalidates the key, the refetch runs Home's broken function,
   it throws, and React Query **keeps the previous data**. The button then downloads the
   **previous calculation's PDF** under the new result. A wrong document, no error.
3. **The id is a guess even when the prefix is right.** "Newest history row" is not "this
   calculation": between the mutation resolving and the refetch landing, `history[0]` is
   the previous row. `storage.createCalculation` already returns the inserted row
   (`storage.ts:30`, `.returning()`), and the handler discards it (`routes.ts:994`).

**Why the prefix went missing.** `API_BASE` is defined three times
(`queryClient.ts:34`, `use-calculations.ts:5`, `use-chat.ts:6`) and applied by hand at every
call site. H-S fixed this exact bug in `History.tsx` and missed the inline copy. The
default query function (`getQueryFn`, `queryClient.ts:96`) and `apiRequest`
(`queryClient.ts:79`) are unprefixed today: latent copies of the same defect, since any
future `useQuery` without its own `queryFn` falls through to one of them.

## Failure modes, named before building

- **F-a — the instance fix.** Adding `API_BASE` to `Home.tsx:19` and stopping. That is what
  H-S did to `History.tsx`. It leaves D53 and the guess (item 3) in place. Refuse it.
- **F-b — the silent strip.** `id` added on the server and not in the web schema. The
  button never renders and nothing errors.
- **F-c — deriving the id.** From history, from a second query, from anything except the
  row the insert returned.
- **F-d — double prefix.** Converting a call site to the typed path while leaving
  `API_BASE +` in front of it. The type should make this unrepresentable. Prove it (M4).
  Casting a call site `as` the path type to get past the checker defeats M4 — same defect.
- **F-e — a test that cannot fail.** Every existing storage mock returns `{ id: 1, ...calc }`.
  A test against that mock cannot tell "returns the inserted id" from "returns 1".
- **F-f — scope creep into the PDF.** D6/D7 live in the renderer. Out of fence. Record, don't fix.
